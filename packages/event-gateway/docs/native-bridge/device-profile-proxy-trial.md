# One-Mac device-profile proxy trial

This is an operator-only, fixed-canary qualification seam. It is not native admission or a deployment recommendation. Automatic turns stay disabled.

## Why a separate controller is needed

The owner Mac's enrolled WARP client rejected `warp-cli mode proxy` with `Invalid setting for this account type.` Both guarded live attempts independently verified healthy original `warp+doh` state and completed restorer shutdown. `allow_mode_switch=true` and the CLI help listing `proxy` did not prove that the enrolled account permits local mode mutation. Do not retry that mutation as root or bypass the refusal.

Cloudflare's supported Local proxy setup uses a device profile with `service_mode_v2: {mode: "proxy", port: 40000}` and MASQUE. A new disabled profile copies the existing Mac profile's writable settings, changing only its canary name/description, exact owner email + Mac + OS-version matcher, precedence, and service mode. The original default, Mac, BYOD, and Mesh profiles remain outside this controller's authority. Before activation, enumerate registrations and confirm the matcher selects only the reviewed Mac; repeat the check immediately before enabling it.

The fixture `scripts/fixtures/device-profile-rollback.mjs` pins one account, the new canary profile ID, its name, and its exact match expression. It has a scheduled handler and no HTTP handler. Deploy it without public routes, workers.dev, previews, Logpush, or application logs, with only its dedicated `STATUS` KV binding. It never accepts commands, URLs, profile IDs, or token values from requests.

## Credential and lease limits

`CF_TOKEN` is a Worker secret, never a source/config value or operator stdout. Cloudflare's [account-token compatibility matrix](https://developers.cloudflare.com/fundamentals/api/get-started/account-owned-tokens/) lists Zero Trust Client Platform as unsupported for account-owned tokens; the account permission-group API marks Zero Trust Write as not selectable. The demonstrated route is a browser-created custom **user token** with **Account Zero Trust Edit** permission ([permission reference](https://developers.cloudflare.com/fundamentals/api/reference/permissions/)) and an expiry no later than 20 minutes after creation. Cloudflare does not scope the user token to an individual device profile, so the fixture's fixed URL and `{enabled:false}`-only PATCH remain essential.

Transfer the token from the browser's new-token confirmation view into the Worker Secret through the trusted tool runtime. Do not expose it in chat, source/config, files, logs, or operator stdout. Record only its token name or ID if available, and expiry, as control metadata. Keep the non-secret `LEASE_SPEC` binding as JSON with exactly `issuedAtMs`, `rollbackAtMs`, and `tokenExpiresAtMs`. Its cleanup deadline is at most 12 minutes after issuance and at least two minutes before token expiry. Missing or malformed bindings cannot produce an armed receipt. Token expiration does not disable the device profile. Revoke the user token and remove the Worker Secret after the trial.

## Admission and proof order

1. Create/read back the canary profile **disabled**; preserve the original profile snapshot and exact request/readback hashes. No client-mode change is part of staging.
2. Deploy the source-pinned rollback fixture unarmed, with no token or lease, and a new dedicated KV namespace. Configure a once-per-minute Cron schedule. Observe a fresh actual scheduled `unarmed` receipt through KV before arming; list the invocation-specific `commits/<scheduledAtMs>/<observationId>` records and require a selected commit to match its corresponding `observations/<observationId>` value byte-for-byte. Each invocation uses a fresh UUID, including retries with the same scheduled time. The observation is written first and its unique commit marker last; an isolated observation is not a complete scheduled proof. There is no shared `latest` key: overlapping runs cannot overwrite each other's observations or commits, and listing order is not evidence of execution order. Reject malformed or mismatched pairs, and require both observed and scheduled times to be within the preceding 90 seconds (allowing at most 30 seconds of future clock skew). Schedule configuration alone is insufficient. Allow for Cron propagation, which can take several minutes.
3. Prove the actual disable actuator without changing any device's mode. While the canary is disabled, temporarily set its matcher to the contradiction `os.name == "mac" and os.name == "linux"` and verify it exactly; a scalar OS name cannot satisfy both conditions. Arm a short qualification lease and observe its fresh scheduled `armed` receipt, then enable only this inert profile. Require an actual scheduled GET/PATCH/GET cleanup, matching committed `disabled` receipts with three API calls, and independent API `enabled:false` readback. Restore the intended owner-Mac matcher only while the profile is independently confirmed disabled. Revoke that qualification token before issuing the actual-trial token. Reading an already-disabled profile alone does not prove the write/disable path.
4. Issue/inject the actual-trial token and fresh bounded lease. Observe a fresh `armed` scheduled receipt matching the pinned profile and the exact current lease deadline, with its observed and scheduled times no earlier than the current lease issuance. At activation, recheck that the deadline still leaves enough time for the bounded trial and immediate disable; an old `armed` receipt cannot authorize activation after its deadline. Do not infer current profile state from receipt ordering; independently read the profile immediately before enabling it. Bind the deployed source/settings and receipt to the admission record, and repeat the unique-device/profile drift checks. Only then enable the canary.
5. Poll bounded readbacks for the exact active profile ID, healthy proxy mode, MASQUE and the fixed root-owned local listener. Then make one guarded Event runtime-status request over the explicitly configured localhost transport. Require the existing authenticated `409 native_binding_unqualified` response. It proves transport authentication, not node-proof validation or native admission; do not enable automatic turns.
6. Disable the canary immediately after the observation, even on failure. Independently, at/after its deadline the Cron handler GETs only the pinned profile, checks its saved ID and boolean enabled state, PATCHes only `{enabled:false}` if necessary, and verifies the same ID and `enabled:false` with a separate GET. Mutable name, match, or service settings never veto disabling this owned temporary ID; those fields are admission checks, not cleanup authority. API, timeout, response-size, or malformed-identity failures never establish successful cleanup. Later Cron invocations retry cleanup; no retry re-enables anything.
7. Require independent API-disabled readback, the client's original profile/mode and healthy status, unchanged enrollment config/key, and complete child cleanup. Preserve failed/partial records. Then revoke the child token, remove its secret, stop the schedule, and delete only the temporary Worker, its KV namespace and the disabled canary profile. Verify absence; retain the original profile snapshot and immutable local evidence.

Cron execution and device-policy propagation are best effort. The cleanup deadline triggers rollback attempts; it is not a guarantee that the client has restored by that instant. If a fresh receipt or independent API/client readback is missing, the run is unqualified and requires recovery rather than another activation.

## Boundaries and validation

API requests use one fixed HTTPS URL, set Workers-supported `redirect: 'manual'`, and fail closed on every 3xx before parsing or continuing; redirect bodies are canceled without being read. Requests have five-second abort deadlines and stream non-redirect responses under a 16 KiB cap. The `apiCalls` receipt field counts fixed-URL request attempts; it does not prove a network subrequest was dispatched because local request validation may fail first. Receipts contain only fixed identifiers, times, statuses, counts, and safe error codes; no credentials, raw errors, policy contents, or request bodies. KV records are observations, not an admission authority or an append-only audit log. Preserve separately fetched local evidence with hashes.

Fixture tests run in Linux and macOS CI. They must detect early cleanup, wrong target/schema, missing post-PATCH readback, unbounded response bodies, auth/transport failures, and token disclosure. Test causal checks use scratch copies, preserve the actual source, and verify red assertions followed by green restored source.

This host-only profile trial does not start a VM. The later guest route test requires a reviewed combined lifecycle that stops/reaps guest networking before restoring host full-tunnel mode. The older local CLI restorer cannot provide that control for this account, and its 45-second trigger cannot simply be stretched around a VM readiness phase that may consume 60 seconds.
